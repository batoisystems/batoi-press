## Goal

Make Batoi Press a secure, automation-ready publishing system while preserving its principal advantage: a portable PHP and flat-file deployment that works on conventional hosting without a mandatory database, Node.js, Docker, Git, or shell access.

Version 2.0 should let a person safely ask Claude, ChatGPT, Codex, or another MCP client to inspect and update a site. Machine actions must go through the same validation, ownership, versioning, and audit boundaries as admin actions. Generated content must never bypass review or publish merely because it originated from an AI client.

## Product Priorities

### P0: Safe automation contract

Build one internal application-service layer and require the Admin UI, JSON API, and MCP tools to use it. Controllers must not be duplicated as an API. The service layer owns validation, sanitization, authorization decisions, revisions, audit metadata, and file mutations.

The initial automation surface should support:

- Site identity and capability discovery.
- Listing and reading pages and posts.
- Creating drafts.
- Updating a draft with a required expected revision.
- Requesting publication as a distinct, more privileged action.
- Reading media metadata and obtaining stable asset URLs.
- Reading menus, taxonomies, templates, and content-health findings.

Deletion, theme source editing, update installation, user administration, token administration, raw filesystem access, arbitrary URLs, arbitrary PHP, and arbitrary HTML execution are not MCP tools in the initial 2.0 release.

### P0: Security and trust

- Machine tokens are random, shown once, stored only as password hashes, scoped, expiring, revocable, and attributable to an issuing user.
- OAuth uses Authorization Code with PKCE and current MCP discovery metadata. Do not build token validation or OAuth protocol logic ad hoc; use an audited, maintained implementation suitable for bundled PHP distribution or a documented Batoi identity broker.
- Separate scopes for reading, drafting/updating, publishing, media mutation, site configuration, and audit access.
- Require step-up/MFA re-authentication for token creation, OAuth consent, publish grants, user administration, update/rollback, and other sensitive owner actions.
- Require optimistic concurrency for every machine write so an agent cannot silently overwrite a newer human or agent revision.
- Require idempotency keys for creates, publishes, uploads, and other retry-sensitive operations.
- Keep read and write tools separate. Tool names, descriptions, annotations, and responses must make side effects unambiguous so clients can apply approval policies.
- Record actor, client, token grant, tool/API operation, correlation ID, target revision, resulting revision, outcome, and safe field-level change summary. Never log credentials or full sensitive prompts.
- Default all AI-assisted output to suggestion or draft state. Publishing requires an explicit publish call and publish scope.

### P1: Editorial and content capabilities

- Workflow states: draft, in review, approved, scheduled, published, archived.
- Review assignments, comments, approval history, scheduled publish/unpublish, and preview links with bounded expiry.
- Categories, tags, canonical URLs, redirects, Open Graph/social metadata, structured data, and content relationships.
- Reusable content blocks/patterns without making stored content dependent on a JavaScript renderer.
- Content-health checks for broken links, missing alt text, missing metadata, stale content, orphan pages, and redirect conflicts.
- Bulk operations with preview/dry-run, bounded item counts, and one audit correlation ID.
- Import/export for Markdown and structured JSON while retaining sanitized HTML as the stable rendering contract.

### P1: Integrated Batoi AIF

Batoi AIF is a first-class integrated feature of Batoi Press. It owns assisted-authoring policy, prompts, context preparation, provider routing, usage controls, audit metadata, and the review boundary. OpenAI, Anthropic, Batoi-hosted inference, or another service may be configured behind AIF, but those services do not replace the Batoi AIF product surface or contract.

Keep inbound MCP automation separate from outbound AIF model-provider calls. MCP lets an authorized external client operate Press; AIF provides native intelligence inside Press. A site can support MCP without sending content to an AIF provider, and AIF can assist an administrator without exposing the site through MCP.

Opt-in assisted features should include:

- Outline and first-draft suggestions.
- SEO title/description and social-copy suggestions.
- Summaries, excerpt generation, tags, internal-link suggestions, and content refresh suggestions.
- Accessible alt-text suggestions with explicit human review.
- Translation drafts with locale and glossary context.
- Content transformation between approved templates or tone profiles.

Batoi AIF provider adapters may support Batoi-hosted intelligence, OpenAI, Anthropic, or another configured service behind a stable AIF contract. Credentials stay outside public files and content. Administrators control which fields may leave the installation, retention expectations, quotas, model/provider choice, and feature flags. Prompt injection from site content is treated as untrusted input; content cannot grant tools, scopes, or publication permission.

### P1: Security hardening

- TOTP and WebAuthn/passkey MFA with recovery codes and enforced owner protection.
- Idle and absolute session lifetimes, session inventory/revocation, password rehashing, login notifications, and optional trusted-device controls.
- Content Security Policy rollout with nonces/report-only validation first, plus HSTS on HTTPS, Referrer-Policy, Permissions-Policy, frame restrictions, and consistent cache controls.
- MIME-signature validation for every upload, robust SVG sanitization or raster-only policy, archive budgets, image decompression limits, and optional malware-scanner hook.
- Encrypted secret storage using a host/environment key; secrets are never written to tracked configuration, exports, backups without encryption, logs, or release packages.
- Signed update manifests/packages using an offline release key, with key rotation and checksum retained as an additional integrity check.
- Backup encryption option, restore drills, release SBOM, dependency/license inventory, security contact, vulnerability disclosure, and supported-version policy.
- Rate limits by IP, user, token, client, and operation; bounded response sizes; pagination ceilings; request-body limits; and optional IP allowlists.
- SSRF protections for every outbound fetch: HTTPS allowlists where possible, DNS/IP validation, redirect limits, timeouts, size limits, and private-address denial.

### P2: Operations and ecosystem

- Webhooks for publish/update/media events with signed payloads, delivery history, retries, replay protection, and secret rotation.
- Health/status endpoint that reveals no secrets and separates public liveness from authenticated diagnostics.
- Backup scheduling and retention policies compatible with cron when available and manual operation when it is not.
- Optional search index generated from flat files; index data is disposable and rebuildable.
- Optional Batoi Workspace fleet visibility, managed policy, centralized OAuth identity, security posture, and assisted upgrades without making Workspace mandatory for a standalone site.
- Extension hooks with declared capabilities and isolation boundaries; no implicit execution of uploaded PHP extensions.

## Automation Architecture

```text
Admin UI -----\
JSON API ------> Application services -> validators/policies -> repositories -> flat files
Remote MCP ---/          |                       |                 |
                         +---- audit log --------+---- revisions --+
```

### Versioned JSON API

Use `/api/v2/...` with JSON request and response bodies, bearer authorization, stable error codes, pagination cursors, result limits, correlation IDs, and `ETag`/revision preconditions. Prefer resource-shaped endpoints over controller-shaped RPC. CORS remains disabled unless explicitly configured with exact origins.

### Remote MCP server

Expose a single configurable Streamable HTTP endpoint, proposed as `/mcp`, with protocol-version negotiation and standard initialize, tools, resources, and logging behavior. The server must be reachable over HTTPS for cloud-hosted Claude/ChatGPT connections. Private installations should use a supported secure tunnel or an optional Batoi-hosted gateway rather than disabling authentication or exposing an admin session.

Initial tool families:

- `site_get`
- `page_list`, `page_get`, `page_create_draft`, `page_update_draft`, `page_publish`
- `post_list`, `post_get`, `post_create_draft`, `post_update_draft`, `post_publish`
- `media_list`, `media_get`
- `taxonomy_list`
- `content_health_check`

Initial resources may expose the site profile, content schemas, allowed templates, taxonomies, and individual read-only content records. Resource and tool outputs must be bounded and must not expose filesystem paths, password hashes, tokens, secrets, private logs, or unpublished content without the matching scope.

### Authentication modes

1. Hashed personal/machine access tokens are the first developer and test foundation. They are suitable for scripts, controlled API clients, and server-to-server calls that can send a bearer token.
2. OAuth 2.1 with PKCE is the required end-user remote MCP experience for Claude and ChatGPT. It uses per-user consent, exact redirect validation, short-lived access tokens, rotating refresh tokens, resource/audience binding, scope enforcement, revocation, and no token passthrough.
3. A Batoi Workspace broker may provide hosted identity and private-site tunneling, but a standalone public installation remains possible.

## Phased Implementation

### Phase 0: Contract and threat model

Deliverables:

- This plan, protocol decision records, data-flow diagram, threat model, and compatibility matrix.
- Explicit stable and experimental tool/API declarations.
- Migration fixtures covering representative `1.8.0` content and customized config.

Exit gate:

- No externally reachable machine-write route exists until authorization, revisions, idempotency, audit attribution, rate limiting, and tests are ready together.

### Phase 1: Machine-access and write-safety foundation

Deliverables:

- Hashed, scoped, expiring, revocable access-token repository.
- Owner-only token administration and secure one-time display.
- Application services and policy objects shared by admin/API/MCP.
- Atomic JSON/HTML commits, per-resource revisions, preconditions, locks, and idempotency records.
- Audit correlation and safe change summaries.

Acceptance:

- Plain tokens cannot be recovered from storage or listing responses.
- Invalid, expired, revoked, incorrectly scoped, or malformed tokens fail closed.
- Concurrent writes produce a conflict and preserve both the current file and its history.
- Retried creates/publishes with the same idempotency key do not duplicate effects.

### Phase 2: Read-only API and MCP

Deliverables:

- `/api/v2` discovery and read endpoints.
- `/mcp` Streamable HTTP endpoint with read-only tools/resources.
- Token authentication, per-operation rate limits, request limits, structured errors, and audit events.
- Setup documentation and tested configurations for compatible developer clients.

Acceptance:

- Claude/ChatGPT-compatible clients can discover site capabilities and read only the content allowed by granted scopes.
- Unauthenticated, incorrectly scoped, cross-site, oversized, traversal, and protocol-invalid requests fail safely.

### Phase 3: Draft writes and OAuth

Deliverables:

- OAuth 2.1/PKCE discovery, consent, token, refresh, revocation, and audience validation through the selected audited implementation.
- Draft-create and revision-checked update tools/API endpoints.
- Separate human-readable approval information for mutating tools.
- Preview/diff response before or after mutation as appropriate.

Acceptance:

- Claude and ChatGPT can connect through a normal OAuth consent flow and create/update drafts without receiving admin credentials.
- A draft scope cannot publish, change users, change secrets, install updates, edit PHP, or delete content.

### Phase 4: Publishing and editorial workflow

Deliverables:

- Review, approval, scheduling, taxonomy, redirect, and explicit publish operations.
- Publish scope and optional policy requiring in-product human approval even when a client holds the scope.
- Webhooks with signing and replay protection.

Acceptance:

- Publication is attributable, revision-safe, reversible through history, and independently governable from drafting.

### Phase 5: Assisted authoring and security completion

Deliverables:

- Integrated Batoi AIF services, guarded provider adapters, and assisted-authoring actions.
- MFA/session/security-header/upload/secret/update-signature hardening.
- Security diagnostics, operator runbooks, privacy controls, quotas, and retention policy.

Acceptance:

- AI provider calls remain disabled by default and disclose exactly what content is sent.
- Generated suggestions cannot self-authorize tools or bypass editorial state.
- Security verification and release-signature checks pass in supported hosting modes.

### Phase 6: Release candidate, migration, and publication

Deliverables:

- `2.0.0-rc` migration rehearsal against a copy of the testsite.
- Full regression, protocol, security, browser, update-from-1.8.0, rollback, static-export, and artifact tests.
- Final documentation, release notes, verified artifacts, testsite synchronization, and `batoi-www` publication.

Acceptance:

- Existing content, themes, URLs, installer lock, and supported customized settings survive upgrade and rollback.
- Publication files exactly match locally verified SHA-256 values.

## External Standards Notes

The implementation should follow the current MCP authorization specification: HTTP authorization is based on OAuth 2.1 conventions, protected-resource and authorization-server metadata, PKCE, HTTPS, exact redirect validation, short-lived tokens, and resource/audience binding. Tokens intended for another resource must not be accepted or passed through.

Current OpenAI guidance supports remote MCP servers over Streamable HTTP or HTTP/SSE, supports bearer/OAuth authorization, tool filtering, and per-tool approval policies, and warns that remote MCP servers are a material data-exfiltration trust boundary.

Current Claude guidance supports custom remote MCP connectors reached from Anthropic's cloud infrastructure and emphasizes OAuth permissions, trusted servers, prompt-injection awareness, disabling unnecessary tools, and careful approval of write actions.

These external client capabilities can evolve during implementation. Re-check the official OpenAI, Claude, and MCP documentation when Phase 2 and Phase 3 begin instead of pinning client-specific behavior from this planning date.
